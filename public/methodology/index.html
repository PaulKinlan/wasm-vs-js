Benchmark Principles

Measurement Methodology & Execution Scopes

A WebAssembly benchmark can measure a 0.08 ms in-memory arithmetic loop or a 35 ms end-to-end Web Worker task on the exact same page. This document defines each timer boundary, explains why Worker Wasm pipelines often run slower than in-memory kernels, and documents how Track A baselines and Track B optimizations stay isolated.

Timer Boundaries

1. Four Distinct Measurement Scopes

Every timing table on this site declares which scope it measures. Speedup ratios are computed strictly within the same scope; dividing an in-memory kernel median by an end-to-end worker task time mixes incompatible work.

Pipeline Diagnostics

2. Why "Worker Wasm" Is Often Much Slower Than Expected

On many benchmark cards and detail pages, Worker Wasm (Task Pipeline scope) takes 5 ms to 60 ms per iteration while the same algorithm in Kernel Compute scope takes 0.05 ms to 2 ms — and Worker Wasm sometimes trails Worker JavaScript on the exact same page. Auditing all 49 runnable browser worker scripts in public/unified-runner.js isolates four concrete causes.

Hypothesis A: Is the Wasm runtime slower inside a Web Worker?

No. Dedicated Web Workers use the exact same V8 Liftoff baseline compiler and TurboFan optimizing tier as the main window thread. When a worker caches its instantiated WebAssembly.Instance across messages, inner kernel execution matches main-thread Kernel Compute speed.

Hypothesis B: Is postMessage message passing the bottleneck?

Rarely for control messages; yes when cloning large buffers without transfer. Structured-cloning a small command payload ({ runId, target: "wasm" }) and returning a small summary object across threads costs roughly 0.05–0.30 ms. Message passing dominates only when an application structured-clones megabytes of typed arrays or deep object graphs on every call instead of transferring buffer ownership (Transferable) or mutating persistent worker memory.

Hypothesis C: Asymmetric per-task loading & instantiation inside workers (Primary Cause)

JavaScript and WebAssembly are loaded asymmetrically inside most contract workers in this repository:

  • Worker JavaScript loads once per worker lifetime: The worker file imports its JS implementation via a top-level ES module statement (import { runJs } from "./workload.js"). When unified-runner.js reuses that worker across 3 warm-up runs and 30 timed iterations, V8 parses the JS source once at worker startup and keeps the hot TurboFan machine code resident in memory. Steady-state JS tasks perform zero network fetches and zero module compilations.
  • Worker WebAssembly re-fetches and re-instantiates per task in 45 of 49 workers: To enforce strict self-contained contract attestation on each run, 33 reused workers keep JS warm at module scope while executing fetch(wasmUrl) (mostly { cache: "no-store" }), crypto.subtle.digest("SHA-256", bytes), and WebAssembly.instantiate(bytes) inside onmessage on every Wasm task; 8 reused workers dynamically re-verify and re-import runtime bundles per message; and 4 single-use workers respawn a fresh worker isolate per sample. Every steady-state Wasm sample in those 45 benchmarks therefore pays Liftoff compilation, fresh 64 KiB–16 MiB linear-memory page allocation and zero-filling, and cold first-call execution before running a single arithmetic instruction. Hypothesis D: End-to-end fixture setup & full-output verification inside the task

Contract workers verify complete outputs inside the timed task boundary. For example, ml-gemm fetches an 8 MiB reference.f64 tensor and a 4 MiB bounds.f32 tensor and validates all 1,048,576 output floats on every task. When a kernel finishes in 0.25 ms while fixture loading, instantiation, and verification take 18 ms, 98.6% of the reported Worker Pipeline duration is non-kernel lifecycle work. Check the Steady-State Network diagnostics and compare Task Pipeline against Kernel Compute on each benchmark page to see the exact split.

Production Checklist: How to Build Fast Worker Wasm

  1. Compile and instantiate once per worker: Store const wasmReady = WebAssembly.instantiateStreaming(fetch(url)) at module scope in the worker so onmessage awaits an already-resolved instance.
  2. Reuse a pinned linear-memory arena: Allocate scratch regions once inside memory.buffer instead of calling new WebAssembly.Instance() or growing memory on each task. Across the 45-workload auto-research log, reusing a pre-instantiated instance and arena is measurably faster whenever kernel compute is under ~5 ms.
  3. Coarsen task granularity: Send batches of frames, records, or blocks per postMessage rather than dispatching thousands of micro-tasks across threads.
  4. Transfer large buffers zero-copy: Pass ArrayBuffers in the postMessage(payload, [payload.buffer]) transfer list or use SharedArrayBuffer when cross-origin isolation is enabled.

Progression Pipeline

3. Three-Stage Kernel Evaluation & Track Isolation

Within Kernel Compute scope, every multi-language benchmark separates compiler parity from target-specific tuning:

  1. Stage 1 — Core Baseline (JS vs Handwritten WAT): Compares idiomatic JavaScript against hand-authored WebAssembly Text format (.wat) compiled directly via wat2wasm without an optimizing C/Rust compiler in between.
  2. Stage 2 — Multi-Language Comparison (Track A Controlled): Implements the identical algorithm and data layout across C (clang -O3), C++ (clang++ -O3), Rust (rustc -O), AssemblyScript (asc -O3), and Dart (dart compile wasm) without target-specific SIMD intrinsics or loop re-tiling.
  3. Stage 3 — Idiomatic & Hardware Optimizations (Track B & Isolated Standalone Auto-Research): Evaluates JavaScript loop/workspace optimizations (js-opt), SIMD128 vectorization (-msimd128 -funroll-loops), cache-blocked loop tiling, call-boundary batching, and linear-memory arena reuse. Hand-tuned Track B entries run live in the browser tab and report speedup strictly against their own language's Track A baseline. Pre-computed auto-research SIMD128 binaries (/artifacts/autoresearch/) and 5-dimension profiles (/data/autoresearch-log.v1.json, /docs/autoresearch-log.md) were captured offline in standalone Deno 2.9 / V8 on Apple M4 Pro and remain explicitly labelled as non-browser CLI diagnostics.

Mechanistic Taxonomy

4. Four Bottleneck Archetypes

Across the 50 workloads, relative JavaScript and WebAssembly speed tracks four structural bottleneck classes:

  • Data-Parallel Numeric & SIMD: Tight typed-array loops without loop-carried dependencies (ml-gemm, audio-fir, numeric-polybench-panel, sum-u32). Contiguous memory layout helps both JS and Wasm (e.g., ml-gemm js-opt gains 1.98× from i/k/j interchange alone), while Wasm v128 SIMD adds 2–4× lane parallelism unavailable to standard JS.
  • Sequential State-Machine & Parsing: Branch-heavy codecs, hashes, regex automata, and wire parsers (archive-zip-workspace, crypto-file-integrity, text-markdown-cms). Loop-carried state prevents SIMD vectorization; V8 JIT and scalar Wasm frequently run near parity unless 64-bit integer bitwise rotations dominate (ChaCha20-Poly1305).
  • Spatial, Graph & WasmGC Heap: Pointer-chasing BVHs, meshes, physics solvers, and managed object graphs (graphics-cpu-path-tracer, cad-mesh-repair, text.gc-document-edit). Representation choices—flat linear-memory slot arrays vs. WasmGC struct graphs (4.70× delta on 10,000 document edits) and native f32 vs. emulated f64 rounding—dominate compiler differences.
  • Real-DOM & Host Boundary: Interactive UI workloads driving live iframe DOM trees (base-dom-todomvc-journey, dom-keyed-list-mutation, vdom-diff-patch-demo). UTF-16 string marshaling, command-stream decoding, and browser style/layout recalculation bound end-to-end latency.

Measurement Disciplines

5. Distributions, Cold Trajectories & Visual Evidence

  • Static Payload Footprint: Binary and source byte counts are reported separately from in-memory execution latency.
  • Cold Initiation vs Warm Distribution: First-invocation compilation/tier-up latency is preserved separately from the warm steady-state median, interquartile range (IQR), min, max, and 95% confidence interval.
