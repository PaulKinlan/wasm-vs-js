Empirical Synthesis · Four Bottleneck Regimes

What governs Wasm vs. JavaScript in practice

No universal JavaScript-versus-Wasm ratio exists because four distinct runtime mechanisms govern different application shapes. Click any linked workload below to verify that regime in your own browser tab.

1. Lifecycle & Instantiation

45 / 49 workers

In the 50-test worker lifecycle audit, 45 of 49 self-attesting contract workers compile a fresh WebAssembly.Instance per task while 33 keep JavaScript warm. Standalone Deno/V8 probes (M4 Pro) measure up to 15.5× overhead on pcap-decode and 7.8× on sum-u32 when instances are not reused.

2. Data-Parallel SIMD128

12 / 45 ≥ 1.05×

Compiling 45 kernels with -msimd128 -funroll-loops emitted v128 instructions in 36 binaries, yet accelerated 12 (audio-fir 3.20×, ml-gemm 2.37×, gltf-viewer 2.03× in standalone Deno/V8). Branchy state machines (sha256, zip, markdown-cms) stay near 1.00×.

3. Cache Stride vs. Language

1.98× JS · 4.43× Wasm

On ml-gemm (128³ strict f32), Track A C, C++, and Rust sit within 6% (0.86–0.92 ms). Switching JavaScript to i/k/j row-streaming (Track B js-opt) halves JS latency (3.01 → 1.52 ms, 0 ULP drift); adding 4-wide f32x4 SIMD128 (c-ikj-simd) reaches 0.20 ms.

4. WasmGC & Numeric Width

4.70× heap cost

On text.gc-document-edit (10,000 edits), Dart/WasmGC's managed _Node reference graph runs 4.70× slower (0.635 ms vs 0.135 ms) than non-allocating C slot arrays. On ml-gemm, emulating absent native f32 scalars in f64 costs ~40×.
