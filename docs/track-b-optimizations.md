# Track B — independently optimized variants

`PLAN.md` defines two tracks. Track A is the controlled comparison: one algorithm,
byte-identical inputs, no target-specific substitution. Track B is the other half —
each target may use production-plausible techniques, and every change carries an
optimization log.

Track B has been in `PLAN.md` since M0 and in the taxonomy since M2. Until this
document, no Track B variant existed in any manifest, and the page at
`/benchmarks/track-b/` imported a module that was never written. This file is the
program spec: what a Track B variant is, what it must prove, and how it lands.

Page: `/benchmarks/track-b/`. Registry: `/data/track-b.v1.json`, generated by
`scripts/build-track-b-registry.ts` and gate-checked.

## What Track B measures

The pair (Track A baseline, Track B variant) for one language on one workload. The
published quantity is the improvement over _that target's own_ Track A baseline, plus
absolute time. A Track B row is never compared against another language's Track A row,
and never enters a Track A aggregate.

Concretely, for `ml-gemm` the C lane would carry `c` (Track A, the frozen i/j/k triple
loop) and `c-tiled` (Track B, the same arithmetic reordered into cache-resident
panels). Both are measured; the page shows both and the ratio between them.

## Variant naming

Track B engine keys extend the Track A key with hyphenated technique tags, most
significant first:

```
c              Track A baseline
c-tiled        i/j panel tiling
c-tiled-simd   panel tiling plus explicit v128 lanes
rs-soa         struct-of-arrays layout change
dart-o3        same source, -O3 instead of the default -O1
```

The Track A key is always the bare language key. A Track B key always contains at least
one hyphen. `scripts/build-track-b-registry.ts` relies on the `track` field, not the
spelling, but the spelling must still follow this shape so report rows read unambiguously.

## Manifest fields

A Track B engine entry in `public/benchmarks/multilang-wasm/<workload>.manifest.json`
carries four fields beyond the normal engine fields:

```jsonc
{
  "key": "c-tiled",
  "kind": "linear",
  "file": "gemm_c_tiled.wasm",
  "track": "B",
  "baseline": "c",
  "equivalence": "bit-identical",
  "optimizationLog": "48x48 i/j panel tiling; k loop order and accumulation unchanged"
}
```

- `track` — `"A"` (default when absent) or `"B"`.
- `baseline` — the Track A engine key this variant improves on. Must exist in the same
  manifest.
- `equivalence` — one of the classes below.
- `optimizationLog` — what changed and why it is faster. One sentence minimum, naming
  the mechanism. "Optimized" is not an optimization log.

The registry generator rejects a `track: "B"` entry missing any of `baseline`,
`equivalence`, or `optimizationLog`, so an undocumented Track B variant cannot reach
the gate.

## Output-equivalence policy

This is the decision that blocks most of the interesting optimizations, so it is
settled here rather than per workload.

The repo rule is that the multilang lane never invents a new oracle — every variant is
verified against the workload's existing pinned oracle. That rule stands. What changes
for Track B is that a variant declares _which kind of agreement_ it claims, and the
verification is chosen to match.

### `bit-identical`

The variant reproduces the pinned oracle exactly — same digest, same bytes, same
counters. Required for every optimization that does not reorder floating-point
arithmetic:

- memory layout changes (AoS to SoA, alignment, padding)
- loop tiling that keeps each output element's accumulation contiguous and in the
  original order — for GEMM this means tiling `i` and `j` only
- branch elimination, strength reduction, table lookup
- integer and bitwise kernels of any shape
- allocation and copy removal

This is the default. A variant claiming `bit-identical` and failing the digest is a
correctness failure, published as such, not retried with a looser class.

### `reassociated`

The variant changes the order of floating-point accumulation, so it cannot match a
strict-order oracle bit-for-bit even when it is entirely correct. This covers:

- `k`-blocking in GEMM and any other reduction split across tiles
- SIMD lane accumulation (four partial sums combined at the end)
- FMA contraction, where the intermediate product is not rounded
- vectorized horizontal reductions

A `reassociated` variant must additionally record, against the pinned oracle:

- `maxUlpDeviation` — largest observed ULP difference over the full output
- `maxRelativeDeviation` — largest observed relative difference
- `declaredTolerance` — the bound the variant claims, fixed before measurement

The tolerance is a property of the variant row, not of the oracle. The oracle's own
tolerance is never widened to admit a variant. If observed deviation exceeds the
declared tolerance, the variant is rejected.

> Why not simply forbid reassociation: it would exclude SIMD and cache blocking from a
> benchmark suite about SIMD and cache blocking. Why not simply relax the oracle: it
> would silently weaken every Track A result that shares it.

### `divergent`

Anything else — different algorithm, different precision, reduced work, different
output shape. Not a Track B variant. Either it is a new Track A workload with its own
oracle, or it is a correctness failure.

## Optimization log

Each Track B variant needs a log entry in this file, under its workload heading, with:

1. the mechanism (what the hardware or compiler now does differently);
2. the parameter, if any, and how it was chosen (tile size, unroll factor);
3. whether the parameter was tuned on the measurement machine — a tile size tuned to
   one L1 size is a finding about that machine, and must be labelled as one;
4. the equivalence class and, for `reassociated`, the observed deviation.

Point 3 matters more than it looks. A 48x48 tile chosen because it fits a 128 KiB L1 is
not a portable result; the same binary on a 32 KiB L1 may be slower than the baseline.
Track B publishes the tile size and the cache it was chosen for, and expects the ratio
to move across the device matrix.

## Registry and gate

`scripts/build-track-b-registry.ts` scans every
`public/benchmarks/multilang-wasm/*.manifest.json`, joins page routes and titles from
`public/data/coverage.v1.json`, classifies each engine as Track A or Track B, validates
the required Track B fields, and writes `public/data/track-b.v1.json`.

```
deno run --allow-read --allow-write scripts/build-track-b-registry.ts
deno run --allow-read scripts/build-track-b-registry.ts --check
```

The `--check` form runs as a static stage in `scripts/check-parallel.ts`, alongside the
`coverage` stage. `deno.json` is deliberately not modified: every artifact manifest pins
its sha256, so adding a task there would force a transitive rebind of dozens of
manifests.

## Current status

Eighteen Track B variants are built, verified, and wired across two workloads (`ml.gemm.v1`
and `numeric.polybench-panel.v1`), spanning C, C++, Rust, AssemblyScript, and Dart/WasmGC.
Seventeen are `bit-identical` to the pinned oracle and one (`c-simd-dot` on `ml.gemm.v1`)
is `reassociated` with measured ULP and relative deviation bounds (`maxUlpDeviation: 31488`,
`maxRelativeDeviation: 0.002152`, `declaredTolerance: 0.005`). Across the 45 multi-language
manifests there are 250 Track A engine rows and 18 Track B variant rows. `/data/track-b.v1.json`
reports the split.

Track A baselines continue to use the controlled compiler flags, while Track B variants
enable `targetFeatures: ["simd128"]` (`-msimd128` in Clang, `-C target-feature=+simd128`
in `rustc`) or dart2wasm optimization levels (`-O2`, `-O3`, `-O4`):

| Language       | Track A Flag            | Track B Flags / Features             |
| -------------- | ----------------------- | ------------------------------------ |
| C / C++        | `-O3 -ffp-contract=off` | `+ -msimd128` (via `targetFeatures`) |
| Rust           | `-O`                    | `+ -C target-feature=+simd128`       |
| AssemblyScript | `-O3`                   | loop-interchanged & tiled sources    |
| Dart           | default `-O1`           | `-O2`, `-O3`, `-O4`                  |

## Optimization logs

### `ml.gemm.v1` — C, C++, and Rust (`ikj`, `tiled`, `ikj-simd`, `simd-dot`)

Ten native-compiler Track B variants on `ml.gemm.v1` (`128×128×128` strict `f32`), built
via `scripts/build-multilang-kernels.ts --write` (which compiles individual manifests
without touching unrelated committed artifacts) and verified against the pinned oracle in
`tests/multilang-gemm.test.ts` and `tests/multilang-engine-agreement.test.ts`:

- **`c-ikj`, `cpp-ikj`, `rs-ikj` (`bit-identical`):** Loop interchange `i/j/k` → `i/k/j`.
  Each inner `j` iteration streams `B[t, 0..n]` contiguously along a row instead of
  striding down a column (`128 * 4 = 512` bytes per step), while accumulating into
  `out[i, j]` in the exact `t = 0..k-1` order required by IEEE-754 single-precision
  addition. Yields **1.21×** (`c-ikj`), **1.18×** (`cpp-ikj`), and **1.26×** (`rs-ikj`).
- **`c-tiled`, `cpp-tiled`, `rs-tiled` (`bit-identical`):** `32×32` `i/j` panel tiling
  with an unsplit `k` loop so each output cell still accumulates `t = 0..k-1` in strict
  order. Yields **0.97×** (`c-tiled`), **0.92×** (`cpp-tiled`), and **0.96×** (`rs-tiled`),
  confirming across LLVM C, C++, and Rust codegen what `asc-tiled` showed: at `128³` the
  three matrices (`3 × 64 KiB = 192 KiB`) already fit in L1d/L2 on Apple Silicon, so
  `i/j` tile-boundary loop overhead slightly outweighs capacity-miss reduction when `k`
  stays unrolled/streamed in `i/j/k` order.
- **`c-ikj-simd`, `cpp-ikj-simd`, `rs-ikj-simd` (`bit-identical`):** Combines `i/k/j`
  row-streaming with `wasm32` `v128` SIMD (`-msimd128` / `-C target-feature=+simd128`)
  and `__restrict` pointer aliasing (or slice indexing in Rust). Why is a **4.43×** SIMD
  speedup still **bit-identical** (0 ULP deviation)? Because in `i/k/j` order the inner
  `j` loop updates 4 independent output columns `out[i, j..j+3]` in parallel using
  `f32x4.mul` + `f32x4.add`. Each lane `j` still accumulates its scalar products
  `A[i, t] * B[t, j]` in strict ascending `t = 0, 1, ..., k-1` order with no horizontal
  cross-lane reduction!
- **`c-simd-dot` (`reassociated`):** Transposes `B` into a scratch panel and computes
  each `(i, j)` inner product with an explicit `wasm_f32x4_mul` + `wasm_f32x4_add`
  4-way parallel accumulator followed by horizontal pairwise reduction (`(s0 + s1) + (s2 + s3)`).
  Because 4-lane tree summation reassociates the `k` reduction, it exercises the
  `reassociated` equivalence class: across all 16,384 output elements of the `128×128`
  product, `maxUlpDeviation` is **31,488 ULPs** and `maxRelativeDeviation` is **0.002152**
  (within `declaredTolerance: 0.005`), running **1.79×** faster than scalar `i/j/k` (`0.5021 ms`
  vs `0.8971 ms`), though slower than `c-ikj-simd` (`0.2025 ms`) due to scratch transpose
  and horizontal lane extraction.

Measured (Deno 2.9.0 / V8, arm64 macOS, `128³`, 200 iterations):

| Variant        | Baseline | ms/iter | vs Baseline | Binary  | Equivalence     |
| -------------- | -------- | ------- | ----------- | ------- | --------------- |
| `c`            | —        | 0.8971  | baseline    | 875 B   | exact           |
| `c-ikj`        | `c`      | 0.7419  | **1.21x**   | 914 B   | `bit-identical` |
| `c-tiled`      | `c`      | 0.9250  | 0.97x       | 1,106 B | `bit-identical` |
| `c-ikj-simd`   | `c`      | 0.2025  | **4.43x**   | 1,038 B | `bit-identical` |

| `cpp-ikj`      | `cpp`    | 0.7341  | **1.18x**   | 914 B   | `bit-identical` |

### `numeric.polybench-panel.v1` — `c-opt`, `c-simd`, `rs-simd`

Three Track B variants on `numeric.polybench-panel.v1` (`2mm`, `3mm`, `atax`, `bicg`,
`gemver`, `gesummv`, `mvt`, `jacobi_1d`, `seidel_2d` in IEEE-754 `f64`), verified across
all 9 kernels in `tests/multilang-polybench.test.ts`:

- **`c-opt` (`bit-identical`):** Adds `__restrict` pointer qualifiers on all 9 kernels,
  hoists invariant row-base address calculations (`i * n`), and reorders `2mm` and `3mm`
  into `i/k/j` row-streaming loops while keeping each cell's `f64` accumulation order
  identical. Yields **1.15×** across the 9-kernel panel (`0.1892 ms → 0.1645 ms`).
- **`c-simd` (`bit-identical`):** Compiles `polybench_opt.c` with `-msimd128`, enabling
  LLVM `f64x2` 2-lane SIMD vectorization across independent columns `j` in the `i/k/j`
  `2mm`/`3mm` matrix products, `gemver` outer-product rank-1 update, and `jacobi_1d`
  stencil sweep without reassociating any scalar reduction. Yields **2.14×** (`0.1892 ms → 0.0884 ms`).
- **`rs-simd` (`bit-identical`):** Compiles `polybench_opt.rs` (`i/k/j` `2mm`/`3mm` +
  hoisted row pointers) with `-C target-feature=+simd128` (`f64x2` vectorization),
  yielding **1.70×** over the Rust Track A baseline (`0.1512 ms → 0.0887 ms`).

| Variant   | Baseline | 9-Kernel Sum (ms) | vs Baseline | Binary  | Equivalence     |
| --------- | -------- | ----------------- | ----------- | ------- | --------------- |
| `c`       | —        | 0.1892            | baseline    | 3,365 B | exact           |
| `c-opt`   | `c`      | 0.1645            | **1.15x**   | 3,701 B | `bit-identical` |
| `c-simd`  | `c`      | 0.0884            | **2.14x**   | 6,753 B | `bit-identical` |
| `rs`      | —        | 0.1512            | baseline    | 4,580 B | exact           |
| `rs-simd` | `rs`     | 0.0887            | **1.70x**   | 6,358 B | `bit-identical` |

### `ml.gemm.v1` — `asc-ikj`, `asc-tiled`

The AssemblyScript memory-hierarchy variants. Both are `bit-identical`, built by
`scripts/build-multilang-asc-opt.ts`, which refuses to report a timing for any variant
whose output digest is not the pinned oracle's.

**`asc-ikj` — loop interchange i/j/k → i/k/j.** The baseline reads `B[t][j]` down a
column in the innermost loop, so every iteration touches a different 64-byte line: 128
distinct lines walked per output element, restarted for every `j`. The interchange
streams `B[t][*]` along a row instead — sequential addresses, full line utilisation,
prefetcher-friendly — and makes `A[i][t]` a loop-invariant scalar.

**`asc-tiled` — i/j blocking, 32×32 panels.** Per-panel working set is 16 KiB of A plus
16 KiB of B, against 64 KiB for the whole of B untiled. The `k` loop is deliberately left
unblocked: blocking `k` would reassociate and would have to carry declared deviations.

Measured (Deno 2.9.0, arm64 macOS, 128³, 200 iterations, four repeat runs):

| Variant     | ms/iter | vs `asc`  | Binary | Oracle |
| ----------- | ------- | --------- | ------ | ------ |
| `asc`       | 1.0263  | baseline  | 213 B  | exact  |
| `asc-ikj`   | 0.8006  | **1.28x** | 308 B  | exact  |
| `asc-tiled` | 1.0004  | 1.02x     | 302 B  | exact  |

### `ml.gemm.v1` — `dart-o2`, `dart-o3`, `dart-o4`

Built by `scripts/build-multilang-dart-opt.ts` from the unmodified
`benchmarks/multilang-wasm/ml-gemm/gemm.dart`. Only the dart2wasm optimization level
changes; the source, the inputs and the oracle are the pinned ones.

| Variant   | Level | ms/iteration | Binary   | Speedup vs `-O1` |
| --------- | ----- | ------------ | -------- | ---------------- |
| `dart`    | `-O1` | 44.3066      | 39,079 B | baseline         |
| `dart-o2` | `-O2` | 43.9589      | 31,585 B | 1.008x           |
| `dart-o3` | `-O3` | 43.8994      | 30,750 B | 1.009x           |
| `dart-o4` | `-O4` | 43.7552      | 30,487 B | 1.013x           |

Moving from the default `-O1` to `-O4` buys 1.3% on this kernel while reducing binary
size by 22% (`39,079 B → 30,487 B`). Dart's GEMM cost is the `f32`-emulation-in-`f64`
arithmetic (`Math.fround` after every operation), not the dart2wasm optimization level.

## Toolchain

Building any Track B artifact needs the same pinned toolchain as Track A: LLVM with a
`wasm32` target (the tests assert `clang version 22.1.8`), `rustc` with
`wasm32-unknown-unknown`, `asc`, and the Dart SDK. Apple's bundled clang has no `wasm32`
target and cannot build any artifact in this repository.
